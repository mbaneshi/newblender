# Wrap Blender in a harness before forking it

**Build the harness around Blender first, as an out-of-process, version-pinned Python layer, and defer any fork until three cheap probes show what only C++ can fix.** The Claude Code components that manage context, plans, policy and tool design transfer to a 3D scene almost unchanged. The ones that lean on the code substrate do not: checkpoints, diffs, grep-style addressing and tests-as-oracle each need an engineered substitute. One property has no substitute at all, a cheap, objective definition of "correct" for aesthetic intent. The Blender source at `d13f752e` (v5.2.2) already contains most of the seams a harness needs. Python can reach the main-thread timer, the depsgraph change stream and the operator schema today. The real C++ needs are narrower than the earlier "five seams" framing suggested: an operator-finished tap, structured operator results, and a non-truncating undo or branch tree. Every existing Blender agent integration found is an unauthenticated `execute arbitrary bpy Python` socket, and none offers transactional undo, reviewable diffs or host-enforced permissions. That gap is the opening for newblender. The recommendation is staged. Phase 0 costs no API money. Probes H1 (headless agent loop), H2 (snapshot and rollback) and H3 (oracle comparison) are budgeted at roughly **USD 34, 22 and 42** of the 200 USD credit, with about 77 USD held in reserve because every per-episode figure is arithmetic on assumed token shapes, not a measurement. The licensing and governance picture favours this order. Blender is GPL, forks must be renamed, and the Foundation says no generative AI is "planned", so an agent-native core is unlikely to be accepted upstream soon.

A scope note on sourcing. Everything below comes from six research notes. Several of their web fetches were summarised by a small model, and some benchmark and paper figures come from abstracts or search snippets. Where a claim is unverified the report says so. Local source citations use `path:line`. `B/` means `source/blender/` in the Blender tree at `/Users/bm/agent-native-lab-data/sources/blender/projects.blender.org/blender/blender`, and `cadcraft/…`, `photocraft/…` and `filmcraft/…` are the shallow clones under `/Users/bm/newblender/labs/`.

## Context and policy layers transfer; the substrate-dependent ones need substitutes

Anthropic defines the harness as "the layer around the model that provides the tools and manages the context the model sees". Its loop is gather context, act, verify ([How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)). The research notes' central observation is that nearly every other component exists to keep the context window small, to make actions reversible or gated, or to supply an external pass/fail signal. The guarantees in turn lean on four substrate properties: text addressability, diffs, git undo and tests as oracle. Claude Code's own docs concede the edge of the guarantee. Checkpoints do not track Bash-made file changes or remote side effects, and they are "not a replacement for version control" ([Checkpointing](https://code.claude.com/docs/en/checkpointing)). A live Blender session, with its in-memory scene, GPU state, add-ons and linear undo stack, sits on the wrong side of that boundary unless the harness externalises scene state into files.

The mapping below is the synthesis of the Claude Code anatomy note, the Blender source notes and the Craft-app teardown. Verdicts are the report's judgement; the evidence behind each is cited in the later sections.

| Repo-harness property | Scene equivalent | Verdict |
|---|---|---|
| Agent loop (gather, act, verify) | Same loop over scene queries, edits, renders | Transfers |
| Tool protocol and MCP | Blender wrapped as an MCP or JSON-lines server | Transfers |
| Context compaction, tool-result clearing, just-in-time retrieval | Summary-first scene views, drill-down on demand | Transfers (raw scene dumps are larger than file reads, so budgets matter more) |
| CLAUDE.md, auto memory, skills | Pipeline conventions, unit and naming rules, rig procedures as plain files | Transfers |
| Plan mode, permission modes | Read tools versus write tools, plan as an edit list | Transfers, provided reads and writes are separate tools |
| Hooks (PreToolUse, PostToolUse, Stop) | Interception on op calls, auto-verify after edits, Stop gated on verifier | Transfers, but enforcement needs process isolation because in-process Python can bypass a wrapper |
| Subagent context isolation | Inspector subagent summarising scene graphs; fresh-context critic | Transfers |
| Grep/Read addressing by stable string | Layered ids: `(type, name, library)`, `session_uid`, custom-property UUID | Needs substitute (no element-level stable ids exist) |
| Edit tool with exact-match failure | Name-resolved RNA writes and wrapped operators with corrective errors | Needs substitute |
| Diff as unit of review | Structural scene diff: depsgraph updates plus RNA snapshot comparison | Needs substitute (no field-level diff, no old values in-tree) |
| Checkpoints and rewind | Per-mutation `.blend` snapshots, named `ed.undo_push` steps | Needs substitute |
| Git branching and worktrees | Parallel headless Blender processes on snapshot copies | Needs substitute (merge by touched id is not free as in text) |
| Tests as oracle | Executable scene assertions plus reference-based checks plus a separate-context VLM judge | Needs substitute for the checkable part |
| Risk and permission classes | External table keyed by `(idname, properties)`, enforced in a sandboxed subprocess | Needs substitute (Blender has no side-effect metadata) |
| Eval methodology (verifiable outcomes, held-out tasks) | Start/goal scene pairs with judge-free metrics | Transfers |
| "Looks right" as a cheap deterministic oracle | None | No substitute |
| Free exact reproducibility and mergeability of edits | None for sculpt, simulation and bake state | No substitute |
| Near-zero-cost exact perception (reading a file) | Renders are approximate and cost about 1,000 to 1,800 image tokens each | No substitute |

The "no substitute" rows deserve their own argument. Code has "tests pass"; a scene has "looks right", which stays a judgement. The academic evidence says the proxies are useful but unreliable in specific, predictable ways. Self-correction without external feedback is unreliable on reasoning tasks ([arXiv:2310.01798](https://arxiv.org/abs/2310.01798)). VLM judges undercall texture defects and overcall missing parts, and in 3D-DefectBench the choice of judge model dominated every other design factor. The best VLM scored geometry MCC 0.403 against 0.519 for a human expert reference, and texture 0.206 against 0.312 ([3D-DefectBench via alphaxiv](https://www.alphaxiv.org/abs/2607.10826.md)). Programmatic geometric checks are the reliable tier, as in CADSmith, which pairs OpenCASCADE measurements with an independent VLM judge and lifted median IoU from 0.8085 to 0.9629 over zero-shot ([arXiv:2603.26512](https://arxiv.org/abs/2603.26512)). The design consequence is a layered verifier: deterministic gates first, rubric-checklist VLM scoring second, pairwise rather than absolute VLM comparison when choosing among candidates, and human approval gates wherever the answer is taste.

Two further transfer facts shape the tool surface. Anthropic's tool-design guidance prescribes few, consolidated tools, concise/detailed response modes, a 25,000-token default cap on tool responses and corrective error strings ([Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)). Blender has roughly 2,023 `ot->idname =` definitions in C++ plus about 334 Python `bl_idname` operators (grep-based and approximate), so a tool-per-operator mapping is the anti-pattern. The sister project nexus-platform-ir reached the same conclusion from its own measurement: 156 tool schemas cost about 16.9k tokens per call, so it moved to about 12 meta-tools with a `describe` discovery step (nexus RFC 0010, as summarised in the seams note). The second fact is cost asymmetry. A GUI step costs one to two thousand image tokens plus overhead, while a `bpy` call returns a few hundred text tokens, and Anthropic's own coding guidance treats screenshots as a verification signal, not the action channel ([Best practices](https://code.claude.com/docs/en/best-practices)).

## The source already holds most seams, but Python cannot trust operators

An independent re-read of the Blender tree confirms all five previously recorded seams at `d13f752e`, with two material corrections. The operator-dispatch seam is real: `WM_operator_poll` sits at `B/windowmanager/intern/wm_event_system.cc:1113`. But poll is called from many places, including UI redraw and greying, so it is a poor observer hook. The better one is `wm_operator_finished` (`wm_event_system.cc:1282`), the common success sink for exec, invoke, Python and modal paths, with call sites at `:1419`, `:1741` and `:2725`. It sees the operator, the undo decision and whether a redo entry registered. A replayable operator log already exists in a debug form. `WM_operator_pystring` (`B/windowmanager/intern/wm_operators.cc:264-339`) renders any operator call as a Python string, and `RPT_OPERATOR` reports appear under `G_DEBUG_WM` (`wm_event_system.cc:1331-1335`). The second correction is that `B/blenkernel/intern/idprop_serialize.cc` serialises IDProperties and is not an operator-schema dumper. Operator schema export is free from Python through `bpy.ops.x.get_rna_type()` (`B/python/intern/bpy_operator_function.cc:707-713`) or would be new C++.

Seams 2 and 3, the main-thread queue and the change stream, are already reachable from Python. `bpy.app.timers` wraps `BLI_timer_register` (`B/python/intern/bpy_app_timers.cc:90-122`), and `depsgraph_update_post` fires after `DEG_evaluate_on_refresh` (`B/blenkernel/intern/scene.cc:2776-2786`) with per-ID `is_updated_transform/geometry/shading` flags (`B/makesrna/intern/rna_depsgraph.cc:213-241`). The change stream is coarse: the granularity is "which ID, which category", there are no old values, there is no operator attribution, and a callback that mutates the scene forces a second evaluation pass (`scene.cc:2788-2815`). Property edits made from Python through ID properties do not get consistent updates, and an in-source disclaimer says so (`B/makesrna/intern/rna_access.cc:2535-2548`). Seam 4, undo, is where C++ buys something Python cannot approximate, and it is the riskiest. `BKE_undosys_step_push_with_type` truncates redo on every push (`B/blenkernel/intern/undo_system.cc:547-553`), so the stack is linear with no branching. The memfile layer writes each ID as its own chunk set and shares identical chunks with the previous step (`B/blenloader/intern/writefile.cc:655-700`, `B/blenloader/intern/undofile.cc:143-158`), which makes "which IDs changed between two steps" derivable in C++ at byte-chunk granularity, with no field-level information. A new primitive turned up: `ID.recalc_up_to_undo_push` and `recalc_after_undo_push` (`B/makesdna/DNA_ID.h:441-452`) record the change category per ID since the last undo push. Seam 5, declarative geometry, holds: `execute_geometry_nodes_on_geometry` is declared at `B/nodes/NOD_geometry_nodes_execute.hh:57-61` and called from the modifier and the node-group tool operator. The claim that its implicitly shared scratch copy is cheap was not opened or measured.

The runtime evidence is what argues for a C++ result record. Probe P01, an earlier runtime run not repeated in this pass, tested 23 region-gated modelling operators headless. Plain poll passed for **0 of 23**; **21 of 23** passed once a never-drawn region was supplied through `temp_override`; only **5 of 23** ran and demonstrably changed state; **4** returned `FINISHED` with no measurable change (`transform.shear`, `sculpt.brush_stroke`, `mesh.rip_edge`, `mesh.rip_edge_move`); **5** sculpt gesture operators segfaulted inside `undo::push_begin_ex`; and 6 returned `CANCELLED` for lack of path input (`/Users/bm/newblender/docs/discovery/probes/p01-context-override.md`). Those categories sum to 20, so three operators are unaccounted for in the note. The probe had no GUI baseline and a single-object scene. Even so, two hard design rules follow. A harness that trusts `FINISHED` is wrong in at least 4 of 23 cases, so every call must be verified by before/after fingerprint. And because a segfault is not catchable from Python, each agent session must run as a subprocess with crash recovery. Platform facts reinforce this. The Python docs state that operators take no data arguments, return only a status, and fail polls with an opaque "context is incorrect" error ([info_gotchas_operators.rst](file:///Users/bm/agent-native-lab-data/sources/blender/projects.blender.org/blender/blender/doc/python_api/rst/info_gotchas_operators.rst)). Calls from Python push no undo by default (`wm_event_system.cc:2002-2016`), and in `-b` mode `bpy.ops.ed.undo()` fails until `ed.undo_push()` is called, which the platform note confirmed empirically on 5.2.2. Threads are unsupported for bpy, and the recommended alternative is multiprocessing ([info_gotchas_threading.rst](file:///Users/bm/agent-native-lab-data/sources/blender/projects.blender.org/blender/blender/doc/python_api/rst/info_gotchas_threading.rst)). The robust path is `bpy.data` and RNA writes, with operators as a wrapped escape hatch.

The Craft apps show what a good agent surface looks like when the engine is designed for it, and what even they lack. CADCraft has one static `CommandSpec` registry (`cadcraft/crates/engine/src/cmd/mod.rs:57-75`) that GUI menus, command line, JSON control channel, CLI and MCP all reach, and its `AGENTS.md` states the rule: "Everything is a command" (`cadcraft/AGENTS.md:29-30`). Commands carry a pure `enabled` predicate returning a human reason (`cmd/mod.rs:159-165`), which surfaces in the catalog as `enabled/disabledReason`. Its most reusable idea is the timeout contract. The bridge marshals each call onto the UI thread through an atomic `QUEUED/STARTED/CANCELLED` state, so a timeout can honestly report either `not-run` (safe to resend) or `may-have-run` (inspect first), and a failed mutation is never auto-resent (`cadcraft/crates/ui-egui/src/control.rs:43-86`, `cadcraft/crates/mcp/src/backend.rs:85-190`). Blender's main-thread timer queue has exactly the same shape. PhotoCraft adds strict envelopes (unknown argument gives `-32602` naming the key, `additionalProperties:false`, MCP annotations with the caveat "Hints do not grant permission"), bearer-token auth, capability-scoped filesystem roots and bounded request and reply sizes (1 MiB request, 8 MiB reply) (`photocraft/crates/automation/src/server/conventions.rs:11-47`, `photocraft/crates/automation/src/security.rs:12-27`). Its tests are agent-surface-only (CADCraft `crates/mcp/src/tests.rs:1`; PhotoCraft's "10 scripted edit tasks over MCP"), and a `panic_hunt` fuzzer calls every command with adversarial parameters (`photocraft/AGENTS.md:72`). All of that is harness mechanics. None of the three has branching, a change stream, per-command risk metadata, automatic post-action verification or a plan and memory layer. CADCraft's undo is whole-document `Arc` snapshots in a linear stack where a new step clears redo (`cadcraft/crates/engine/src/undoctl.rs:80-110`), and PhotoCraft's nearest thing to a branch is duplicating the document (`photocraft/docs/mcp.md:42-45`). The `revision` counter exists in CADCraft's `DocState` but is not surfaced to the agent. One caution on the Craft pattern: tool vocabularies have already diverged between CADCraft (`command_line/execute/inspect_drawing`) and PhotoCraft/FilmCraft (`command_run/command_batch/doc_inspect`), and the three servers share no code (`craft-libs` contains no MCP or registry code). The notes infer that a harness spec should be defined once, with JSON Schema contracts and conformance tests, and this report adopts that.

## Four build routes trade control against GPL, trademark and upstream friction

The options space has four real members. The table summarises; the paragraphs after it give the reasoning and the governance facts.

| Option | What it is | Gains | Costs and risks |
|---|---|---|---|
| A. Out-of-process Python harness | Harness process plus headless Blender worker(s) (`blender -b`, `bpy` module, or `--command` handler); optional UI-mode add-on with timer-pumped socket | Fastest to build; no rebase burden; query, coarse change stream, file checkpoints, risk table, verification all feasible; keeps Blender's full feature set | Cannot get operator attribution, old values, in-memory branching, structured results; subject to P01 crashes and silent no-ops; API breaks per major version (5.0 was large) |
| B. Small C++ patch set | A patch queue (under about 500 lines each): operator tap at `wm_operator_finished`, ring buffer plus Python accessor, expose poll message and `compare_geometry`, `--command agent-serve` skeleton | Closes the observation gaps; changes no behaviour; most upstream-friendly | Still needs a custom build; AI-contribution policy applies to anything proposed upstream; wm_event_system.cc is about 7,000 lines and central |
| C. Long-lived fork | B plus behaviour changes: non-truncating branchable undo with per-ID diffs, structured operator results, explicit-parameter operators, headless-safe edit paths | The only route to real engine-level agent citizenship | Project-sized work in entangled code (edit-mode and sculpt undo, library overrides); permanent rebase cost; must be renamed; GPL source obligations on distribution |
| D. ArtCraft-style new engine | A new Rust engine with a CADCraft-style registry, headless session and MCP | Cleanest harness (everything is a command, from day one); MIT or Apache-2.0 for reuse | Abandons Blender's feature set; the ArtCraft and ArtCraftX apps themselves have no agent surface to inherit |

Option D fails on scope for this credit and this team, but the Craft apps are the right reference for the interface. The teardown found that ArtCraft (a Tauri generation app) and ArtCraftX contain no MCP server and no loopback control port. The only MCP-related code is a backend credential model (`mcp_sessions` with a shown-once private token and a rotating refresh token) and an explicit stub for "Prompted mode" in the 3D scene builder, where an LLM would emit a whole new scene descriptor (`artcraft/frontend/libs/components/pagescene/AGENTS.md:432`, `:177`). The Craft editors (CADCraft, PhotoCraft, FilmCraft) are the ones worth studying. Option C is the destination only if the probes justify it. Option B is where the real engineering sequence begins, because the seams note sizes the work this way: observation and introspection are patch-sized; undo semantics, result records across the operator corpus, and removal of context dependence are projects. These sizes are the researcher's estimates from reading anchor code, with no prototype behind them.

Licensing is straightforward at the file level and unsettled at the boundary. Blender is licensed under GPL, with source headers `GPL-2.0-or-later` and the whole under GPLv3 for binaries ([README.md:35-36](file:///Users/bm/agent-native-lab-data/sources/blender/projects.blender.org/blender/blender/README.md); [blender.org/about/license](https://www.blender.org/about/license/)). The Python API is treated as integral, so published add-ons must be GPL-compliant, and a fork can be distributed under GPL only with source and the Foundation's trademark conditions. An in-house add-on or fork that is never distributed does not trigger distribution duties. The out-of-process route is the grayest: the license page says proprietary use of `bpy` is possible "under certain conditions" without stating them, and the notes found no official statement on a separate process speaking to Blender over IPC (this is not legal advice). nexus-platform-ir forbids GPL dependencies (`/Users/bm/nexus-platform-ir/docs/MASTER_BRIEF.md:154`), so nexus can contribute patterns (typed ops with preconditions and inverses, revision-stamped observation views, append-only logs) but never code. The Craft repos are MIT OR Apache-2.0, so their code could be ported with attribution, except that `artcraft-services` carries a non-OSI "fair source" licence that forbids competing products and `artcraftx` ships no licence file at all; neither should be copied from, and the ArtCraft name and `docs/brand/` assets are reserved trademarks ([NOTICE in each clone]).

Trademark bites the project's own name. Blender's policy requires a fork to "give it a new name and create a unique brand", and using the trademark in a business, product, app or domain name needs prior written permission, though "based on Blender's open source code" is allowed as a secondary statement ([Trademark policy](https://www.blender.org/about/trademark-policy/)). "newblender" is therefore acceptable as an internal codename and a risk as a public product name. This is an inference from the policy text; no one has asked the Foundation.

Governance is the strongest argument against betting on upstream. On 1 May 2026 the Foundation chair stated that "No generative AI functionality is currently available or planned to be integrated in Blender" and converted Anthropic's corporate-patron membership into a one-time donation after community concern ([blender.org](https://www.blender.org/news/upcoming-blender-development-fund-and-ai-policies/)). An AI-contributions policy proposal (v2, 2026-02-01) permits tool use but requires that humans are the only commit authors and `Co-authored-by` names, requires disclosure of significant AI use via an `Assisted-by:` trailer in the v1 wording, and lets reviewers close suspect PRs without review ([devtalk](https://devtalk.blender.org/t/ai-contributions-policy-proposal/44202)). The proposal's scope excludes extensions; a published v3 exists in the handbook but was not retrieved. The community already asked for host-owned permission scopes: a devtalk thread on MCP security argued that the bundled `weak_sandbox.py` "is not a security boundary" and proposed scopes for scene, file, network, add-on registration and subprocess, but one core developer thought Blender probably cannot solve this and the topic was closed as off-topic on 8 September ([devtalk](https://devtalk.blender.org/t/blender-mcp-server-after-claude-mcp-security-for-blender-scripting-3d-agent-notes/45131)). The notes' reading is that observation hooks framed as automation and API work are the only plausibly upstream-friendly changes, while anything labelled agent-native should expect to live in a fork. That reading is the researchers' inference, not a stated Foundation position. The extension platform adds little constraint: manifest `[permissions]` entries (`files`, `network`, `clipboard`, `camera`, `microphone`) are displayed in the UI but the notes found no runtime enforcement, so permission declarations are disclosure and not a boundary, and any sandbox has to be external.

## Recommended architecture: a registry-first harness with a Blender worker behind a Backend trait

The recommendation is Option A now, with Option B's patches queued behind probe evidence and Option C deferred. It borrows the registry-first discipline of the Craft apps and uses Blender's real seams. Targeting the 5.2 LTS line with a version shim is the stable-ish anchor, given that 5.0 broke Actions, the compositor and render-pass names and 5.2 changed Geometry Nodes modifier inputs and socket identifiers ([5.0](https://developer.blender.org/docs/release_notes/5.0/python_api/), [5.2](https://developer.blender.org/docs/release_notes/5.2/python_api/)).

The process model keeps the agent protocol out of Blender's embedded interpreter, which Rhino's Python 3.9 pin illustrates as a trap ([PyPI lamcp](https://pypi.org/project/lamcp/)). A harness process owns the loop, memory, policy and MCP front end. One headless Blender worker per session runs a single main-thread command loop. A CADCraft-style `Backend` trait lets the same method names be served by a headless `bpy` session or by a live UI-mode add-on, with a `control.methods` self-description checked against its documentation by a test. The worker must own its loop through a `--command` handler (`B/blenkernel/BKE_blender_cli_command.hh:26-51`, CLI at `source/creator/creator_args.cc:3162`) or a script-owned loop, because whether `BLI_timer_execute` fires in a pure `-b` session is unproven. Every worker starts with `--disable-autoexec`, as P01 did. Calls carry the `not-run` and `may-have-run` contract, and only the read-only allowlist is auto-retried.

The tool surface is a set of intent-level meta-tools in the nexus and Anthropic style, not a wrapped operator list. The core tools are `scene_query(selector, fields, limit, cursor, format)` with a concise/detailed mode and corrective errors ("object 'Cube.001' not found; closest names: …"); `op_describe` (schema from `get_rna_type`, plus a risk class and preconditions); `scene_edit`, a batch of name-addressed RNA writes and wrapped operator calls that sets its own context through `temp_override` and takes explicit object sets, never inherited UI state; `scene_diff`; `checkpoint`, `restore` and `branch`; `verify(assertions)`; `render_preview`; and notes and plan tools. Raw `run_python` exists only behind a default-deny risk gate. That departs from nexus MASTER_BRIEF section 7, which refuses `run_python`/`eval` tools (`MASTER_BRIEF.md:142-158`), and the departure is deliberate: it is also the comparison arm in H1, since the whole existing ecosystem ships exec-only.

Identity is layered because Blender offers no single stable id. Addressing uses the `(ID type, name, library)` triple that `UndoRefID` itself relies on (`B/blenkernel/BKE_undo_system.hh:32-48`). Within-run stability uses `session_uid` (`B/makesdna/DNA_ID.h:453-457`). Cross-session identity uses an add-on-written UUID custom property, since the notes found no persistent UUID field on `ID`. Element ids for vertices and faces do not exist and edits renumber them, so receipts use attributes or index sets per call. Whether `session_uid` survives save and load is ambiguous (the DNA comment says session-wide and the RNA text reads differently) and needs a one-line test. CADCraft's handle scheme carries a warning: handles issued after an undo may coincide with handles of undone entities an agent still holds (unverified there), so the harness should never recycle ids within a session.

Checkpoints, diffs and branches use files and processes, which are the substrates that actually give rollback in the literature. Every mutating call takes a snapshot only when it changed something. The Crab study found more than 75 percent of agent turns produce no recovery-relevant state, which supports mutation-only granularity ([arXiv:2604.28138](https://arxiv.org/abs/2604.28138)). Snapshots are `save_as_mainfile(copy=True)` outputs in a content-addressed store with a git-like parent pointer, with named `ed.undo_push` steps as the cheap in-session layer. A branch is a new worker process started from a snapshot, which is also the parallel-subagent model and the analogue of git worktrees. A diff pairs the depsgraph update record with an RNA snapshot comparison (transforms, modifiers, material parameters, counts), fingerprinted before and after every call. Reviewable structural diffs and non-truncating history matter because nexus RFC 0007 insists undo be an appended meta-event and never truncation, while Blender truncates by design (`undo_system.cc:547-553`). The harness's own append-only operation journal lives outside Blender and does not rely on the 32-entry `wm.operators` list (`B/windowmanager/intern/wm.cc:252`).

Policy follows mytodo's R0 to R4 scale (`/Users/bm/mytodo/docs/superpowers/specs/2026-10-06-target-architecture.md:255-259`) with "R2 spend" reinterpreted as compute and render cost. Reads and most `OPTYPE_UNDO` scene edits are R0 and R1. `RENDER_OT_render` and the bake operators are R2 with time and frame budgets. Operators that replace the live session or import external data (`WM_OT_open_mainfile`, `WM_OT_read_factory_settings`, `WM_OT_link`, `WM_OT_append`) are R3 with a checkpoint. Saving over files or user preferences (`WM_OT_save_mainfile`, `WM_OT_save_userpref`) is R4. Code execution (`SCRIPT_OT_python_file_run`, `TEXT_OT_run_script`, `script.execute_preset`) and network or package install (`wm.url_open`, `extensions.package_install` and relatives) are R4 and denied to autonomous loops. Only about 30 operators were classified. Class depends on `(idname, properties)`, since `OBJECT_OT_delete` carries `use_global`, and a test that fails loudly when any registered idname is unclassified is the recommended guard. Enforcement needs an OS sandbox around the worker, because Blender's permission manifest is disclosure only and in-process Python can bypass any wrapper. The Foundation's own Lab MCP server states that it runs LLM-generated code "without any guards in place" ([blender.org/lab/mcp-server](https://www.blender.org/lab/mcp-server/)), and the leading community server documents an unauthenticated socket with an off-by-default safe mode ([GitHub](https://github.com/ahujasid/blender-mcp)). PhotoCraft's bearer-token handshake and capability-root pattern is the better local-harness model.

Verification is the Stop hook of this harness. The agent cannot end a turn until a layered check passes: deterministic scene assertions (non-manifold edges, poly budget, bounding box in metres, material slots assigned, modifier order, naming rules, NaN transforms, render completes within N seconds), then reference-based checks against a target if one exists, then a rubric-checklist VLM judge in a separate context fed a six-view oblique render (the default 3D-DefectBench recommends). `compare_geometry` (`B/blenkernel/BKE_geometry_compare.hh:39-66`) is the right shape for machine QA but its Python exposure was not verified. FilmCraft's pattern of returning success with structured warnings, such as `offlineMedia`, is worth copying for missing textures and similar soft failures. Memory and plan layers have no precedent in the Craft products (the plan layer there is development-time only), so they come from Claude Code directly: a short pipeline `AGENTS.md`, skills for procedures, and a JSON feature list with a `passes` flag that agents may only flip, which Anthropic's long-running harness found models alter less than Markdown ([Harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). Subagents split three ways: an inspector that returns a 1,000 to 2,000-token scene summary, a fresh-context critic, and parallel workers on branch snapshots. Anthropic cautions that multi-agent runs cost about 15 times chat tokens and that coding is a weaker fit than breadth-first research ([Multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system)), so parallelism is a late, measured addition.

## Three probes inside the 200 USD credit, cheapest and most informative first

Pricing facts come from the pricing page fetched 2026-10-17 ([Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)). Claude Sonnet 5.5 is **USD 2 per million input tokens, 10 per million output, and 0.10 per million for cache reads**; Opus 5.5 is 4 / 20 with 0.20 cache reads; Haiku 5.5 is 0.10 / 0.50 up to 100k-token prompts. Batch is 50 percent off and stacks with caching, but suits single-shot judge scoring and not interactive tool loops. The notes' reference episode (30 turns, 40k-token average prompt of which 38k are cache hits, 600 output tokens per turn) costs about **USD 0.51 cached and 2.60 uncached on Sonnet 5.5**, so a silent cache failure multiplies spend roughly fivefold. Screenshots add about 1,000 to 1,800 tokens each. All figures below are this report's arithmetic on those assumptions, with a 0.65 to 0.80 USD per-episode allowance for image-bearing runs, and are not measurements. Anthropic's own analysis found token usage explained about 80 percent of performance variance on BrowseComp, so configurations must be compared at equal spend and the log must record tokens per episode and `cache_read_input_tokens`.

**Phase 0 (no API spend, about a day).** Settle the premises that make the later numbers meaningful. Test whether timers fire in a pure `-b` session, whether `session_uid` survives save and load, whether `compare_geometry` is bound to Python, whether `bpy.ops.x.poll()` exposes the poll message, and the cost of `save_as_mainfile(copy=True)` on a realistic scene (never measured). Re-run P01's three unaccounted operators and add a GUI baseline for the four silent no-ops, since "needs view data" versus "broken headless" is unresolved. Open the implicit-sharing code to check the cheap-scratch-copy premise behind seam 5. Success is a written yes or no for each, because several downstream designs branch on them.

**H1, headless agent loop with query, apply and verify tools (about USD 34).** Build the registry-first harness with `scene_query`, `scene_edit`, `verify` and `render_preview`. Run 20 realistic tasks with verifiable end states, drawn from BlenderGym-style start/goal pairs where the metric is judge-free ([arXiv:2504.01786](https://arxiv.org/abs/2504.01786)), against two arms: structured meta-tools versus raw `run_python`. That is 40 episodes at roughly 0.65 USD plus an 8 USD pilot of about five episodes to debug the harness. Success criteria are a task-pass rate for the structured arm at least equal to the exec arm at equal token spend, strictly fewer unrecoverable states (crashes and silent no-ops detected by fingerprint), and a cache hit ratio above 90 percent after the first turn. The failure signal that would kill the design is the structured arm losing badly on pass rate because the meta-tool surface cannot express the tasks. The 3D-Agent forum report that a screenshot after each operation was "the most important quality improvement" and that without feedback the agent drifts into "geometry soup" supports including `render_preview` in both arms.

**H2, snapshot and rollback effect (about USD 22).** The mechanics are deterministic and cost nothing in API terms: induce a bad edit, restore, and measure fidelity by comparing the restored scene to the pre-edit fingerprint across edit types (primitives, modifiers, materials, node trees, one sculpt and one simulation-cache case, where this is expected to fail). The paid part tests whether rollback changes agent outcomes: 10 tasks seeded with a trap that a naive path falls into, three recovery strategies (none, undo-stack, file snapshot), 30 episodes at about 0.70 USD. Success is a restoration-fidelity of 100 percent for data-block edits, a measured snapshot cost per call small enough for per-mutation use, and a pass-rate lift for snapshot recovery over no recovery. The literature offers no direct evidence that cheap rollback improves creative-agent success in 3D; BlenderAlchemy keeps the best-so-far program as an implicit revert in its search ([arXiv:2404.17672](https://arxiv.org/abs/2404.17672)), and the OS-level rollback work (DeltaBox, Crab) is about sandboxes. H2 is therefore genuinely new evidence, and its negative result would argue against investing in Option C's branching undo.

**H3, verification oracle comparison (about USD 42).** Compare three verifier conditions inside the loop on 15 tasks (none, deterministic assertions only, deterministic plus VLM judge) at 45 episodes and roughly 0.80 USD, about 36 USD. Separately, validate the judge on stored renders of an injected-fault scene set, in the style of 3D-DefectBench, scoring agreement with the deterministic labels and with the human labels. About 360 Batch judgements at about 1 cent each, built from six-view renders at 10k input tokens, comes to about 5 to 6 USD. Success is that the deterministic tier catches at least the injected geometric faults the VLM catches (a VLM-only gain would be the surprise), that the VLM judge's precision and recall on gross faults are measured rather than assumed, and that adding the judge improves end-state pass rate without raising false rejections of correct work. The same experiment checks whether Haiku 5.5, Sonnet 5.5 or both are adequate judges, since judge model choice dominated every other factor in 3D-DefectBench.

**Remainder and reserve.** About USD 25 buys a headline slice on Opus 5.5 (roughly 20 episodes at about 1.2 USD, 1.5 to 2 times Sonnet's cost; Fable 5.1 would be about 5 times). That leaves roughly **USD 77** unallocated, a deliberately large 38 percent reserve. The notes' campaign split suggested about 15 percent for pilot and debugging, 55 percent for the main matrix, 15 percent for a top-model slice and 15 percent for judging and reruns. This plan spends less on the main matrix because the episode shape is a guess, and it keeps the unspent money for the likeliest overrun, a task set that needs more turns or more images than the reference episode assumes.

Risks are specific. Cache invalidation is the largest budget risk, since changing tool definitions invalidates everything, and tool schemas must therefore stay frozen within a run. P01 shows the Python route can produce crashes and silent no-ops that contaminate results, so every episode runs in a subprocess with fingerprint checks. The API itself moves (5.0 broke many names), so the harness must pin Blender 5.2.2 and the Python 3.13 `bpy` wheel, noting there is no Intel macOS wheel and the headless render timings (EEVEE 256px in 0.38 s, Cycles CPU 16spp in 0.21 s on an M4, trivial scene) say nothing about complex scenes. Model deprecation is a reproducibility risk, as LL3M's retired Claude Sonnet 3.7 backend illustrates ([arXiv:2508.08228](https://arxiv.org/abs/2508.08228)), so prompts and traces must be logged for replay. A final risk is overfitting to the judge: a VLM asked for gaps will find some, which Anthropic's best-practices page flags for reviewer subagents.

## Conclusion

Two things changed relative to the framing of the project. First, the engine-level case for newblender is narrower and better evidenced than "redesign Blender for agents". The seams that matter most are not the ones with the most code: the operator-finished tap and structured operator results fix a failure that P01 measured (silent `FINISHED` and segfaults), whereas branchable undo fixes a hypothesis, namely that cheap rollback helps creative agents, which nobody has tested. H2 is the experiment that decides whether the project-sized work in Option C is worth the rebase and renaming burden. Second, the ecosystem gap is not tool count. Every Blender integration found ships an exec socket, and the Craft apps ship good registries but no checkpoints, diffs, risk classes or verification. Reviewable change sets, enforced permissions, a trustworthy deterministic verifier and speculative branching are the open ground, and most of it can be staked out in Python for under 100 USD before any C++ is written.

The harder implication is political and structural, not technical. The one property with no substitute, a cheap definition of "looks right", means the harness can offer the user better checkpoints and better gates but cannot replace the human at the taste boundary. Design the approval gate as a first-class feature, not a fallback. And because the Foundation's stance makes upstream acceptance of anything labelled agent-native improbable for now, plan the C++ work as two streams from the start: behaviour-neutral observation patches written to survive upstream review, and a clearly separated, renamed fork for the rest, with the project name settled before anything is published.
